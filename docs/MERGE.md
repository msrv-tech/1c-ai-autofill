# Обновление веток конфигураций из ядра (core)

## Как ведём разработку

1. **Обычная разработка (фичи, правки логики)** — делаем в ветке **core**:
   - Редактируем модули, формы, каталоги в `core/xml/`.
   - Коммиты: `git add …`, `git commit -m "…"` в worktree `core`.
   - При релизе ядра при необходимости поднимаем `<Version>` в `core/xml/Configuration.xml`.

2. **Подтянуть изменения в ветку конфигурации** — когда в ветке **core** появились новые коммиты:
   - Переходим в worktree нужной ветки (UNF_Rozn, UNF_Rozn_Fresh, UT_KA_ERP).
   - Выполняем `git merge core`, при конфликтах — см. раздел ниже.
   - В этой ветке при сборке своего релиза поднимаем версию в своём `Configuration.xml` при необходимости.

3. **Отличия только в ветке конфигурации** (редко):
   - Если правка нужна только для одной конфигурации (например, другое размещение кнопки только для UNF_Rozn_Fresh) — правим в соответствующей ветке и коммитим там. При следующем мерже core в эту ветку возможны конфликты — разрешаем, оставляя свою правку.

4. **Итог:** разработка ядра идёт в **core**; ветки конфигураций периодически мержат **core** и собирают свои .cfe для релизов.

---

## Структура репозитория

- **main** — служебная/документационная ветка без `xml`-ядра.
- **core** — ядро расширения: полная xml-выгрузка, включая `Configuration.xml` и `ConfigDumpInfo.xml`. Имя расширения в ядре: `GPT_ОписаниеНоменклатуры`. Ветки конфигураций мержат **core**.
- **UNF_Rozn** — сборка для УНФ / Розницы (то же имя расширения).
- **UNF_Rozn_Fresh** — сборка для 1cfresh (имя расширения: `GigaСhat_ОписаниеНоменклатуры`).
- **UT_KA_ERP** — сборка для УТ / КА / ERP (то же имя расширения).

Отличия между ветками в основном в `xml/Configuration.xml`: имя конфигурации (`<Name>`) и при необходимости версия (`<Version>`). Остальные файлы совпадают с core.

## Как подтянуть обновления ядра в ветку конфигурации

1. Переключиться в нужную ветку конфигурации (например, `UNF_Rozn`).
2. Выполнить слияние с core:
   ```bash
   git merge core
   ```
3. Если возникнут конфликты:
   - В **xml/Configuration.xml** — оставить **своё** значение `<Name>` и при необходимости `<Version>` (не брать из core). Остальные конфликты в этом файле разрешать по смыслу.
   - В **xml/ConfigDumpInfo.xml** — при конфликтах оставлять свою версию или разрешать по смыслу (идентификаторы конфигурации).
   - В остальных файлах (модули .bsl, формы и т.д.) — брать версию из **core**; исключения — осознанные отличия конкретной конфигурации.
4. После разрешения конфликтов — закоммитить результат слияния.

## Рекомендации

- Изменения в общей логике (модули, формы, реквизиты) вносить в **core**, затем мержить **core** в ветки конфигураций.
- В ветках конфигураций хранить только отличия: другой `<Name>` (и при необходимости `<Version>`) в `Configuration.xml`, точечные правки под конфигурацию.
- Версию в `Configuration.xml` в main/core можно поднимать при релизе ядра; в ветках конфигураций — при сборке своего релиза.
