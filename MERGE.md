# Обновление веток конфигураций из ядра (main)

## Как ведём разработку

1. **Обычная разработка (фичи, правки логики)** — делаем в ветке **main**:
   - Редактируем модули, формы, каталоги в `main/xml/`.
   - Коммиты: `git add …`, `git commit -m "…"` в worktree main.
   - При релизе ядра при необходимости поднимаем `<Version>` в `main/xml/Configuration.xml`.

2. **Подтянуть изменения в ветку конфигурации** — когда в main появились новые коммиты:
   - Переходим в worktree нужной ветки (UNF_Rozn, UNF_Rozn_Fresh, UT_KA_ERP).
   - Выполняем `git merge main`, при конфликтах — см. раздел ниже.
   - В этой ветке при сборке своего релиза поднимаем версию в своём `Configuration.xml` при необходимости.

3. **Отличия только в ветке конфигурации** (редко):
   - Если правка нужна только для одной конфигурации (например, другое размещение кнопки только для UNF_Rozn_Fresh) — правим в соответствующей ветке и коммитим там. При следующем мерже main в эту ветку возможны конфликты — разрешаем, оставляя свою правку.

4. **Итог:** основной поток изменений идёт в **main**; ветки конфигураций периодически мержат main и собирают свои .cfe для релизов.

---

## Структура репозитория

- **main** — ядро расширения: полная xml-выгрузка, включая `Configuration.xml` и `ConfigDumpInfo.xml`. Имя расширения в ядре: `GPT_ОписаниеНоменклатуры`.
- **UNF_Rozn** — сборка для УНФ / Розницы (то же имя расширения).
- **UNF_Rozn_Fresh** — сборка для 1cfresh (имя расширения: `GigaСhat_ОписаниеНоменклатуры`).
- **UT_KA_ERP** — сборка для УТ / КА / ERP (то же имя расширения).

Отличия между ветками в основном в `xml/Configuration.xml`: имя конфигурации (`<Name>`) и при необходимости версия (`<Version>`). Остальные файлы совпадают с main.

## Как подтянуть обновления ядра в ветку конфигурации

1. Переключиться в нужную ветку конфигурации (например, `UNF_Rozn`).
2. Выполнить слияние с main:
   ```bash
   git merge main
   ```
3. Если возникнут конфликты:
   - В **xml/Configuration.xml** — оставить **своё** значение `<Name>` и при необходимости `<Version>` (не брать из main). Остальные конфликты в этом файле разрешать по смыслу.
   - В **xml/ConfigDumpInfo.xml** — при конфликтах оставлять свою версию или разрешать по смыслу (идентификаторы конфигурации).
   - В остальных файлах (модули .bsl, формы и т.д.) — брать версию из **main**; исключения — осознанные отличия конкретной конфигурации.
4. После разрешения конфликтов — закоммитить результат слияния.

## Рекомендации

- Изменения в общей логике (модули, формы, реквизиты) вносить в **main**, затем мержить main в ветки конфигураций.
- В ветках конфигураций хранить только отличия: другой `<Name>` (и при необходимости `<Version>`) в `Configuration.xml`, точечные правки под конфигурацию.
- Версию в `Configuration.xml` в main можно поднимать при релизе ядра; в ветках — при сборке своего релиза.
